# VCF 与强制防守

这套实现属于共用 C++ 引擎。原生 Worker、Gomocup 和浏览器 WASM 使用相同代码，
不依赖教师进程、Python、网络或额外模型。

## 增量棋形

`Threats` 缓存双方每个空点的四个方向，区分即时成五、冲四及多个成五点。
每个方向用中心两侧各五格的三进制编码查询规则表；边界和对方棋子都阻断连线。
自由规则允许长连，标准规则只认恰好五连。落子和撤销只更新受影响的四条线，
不扫描整个棋盘重建，也不改动 NNUE 状态。

## 搜索次序

1. 己方有成五点：直接返回合法胜着。
2. 对方有两个成五点且己方不能立即赢：返回必败分及一条成五变化。
3. 对方只有一个成五点：只搜索这一步防守，即使已经到达名义深度。
4. 无必须防守的安静叶节点：若己方有冲四点，尝试 VCF；未证明获胜时继续普通评估。

VCF 枚举全部冲四点。攻击后若防守方能够先成五，立即拒绝该攻击；否则只有一个
成五点时防守被迫堵住，有两个成五点时返回包含实际五连的获胜主变化。
连续冲四的攻击、防守逐步递归，不借助 NNUE 分数判断证明是否成立。

## 预算与结果

默认每次 VCF 最多访问 1,024 个攻击节点、延伸 32 手，同时受整个搜索的时间、
取消和节点预算限制。全局 nodes 还包含 VCF 分支的预算检查工作，因此与旧版本
纯 Alpha-Beta 的 nodes 定义不同，不应直接用 nodes/s 比较性能。

求解结果明确区分 `win`、`no_win`、`unknown`：`win` 带一条合法成五变化；
`no_win` 只表示没有找到该定义下的连续冲四胜法；节点/深度预算耗尽为 `unknown`。
后两者都不能解释成局面必败。异常和预算中断自动撤销棋盘与棋形，NNUE 累加器
仍恢复到进入搜索前的状态。

`SearchOptions.vcf` 可在 C++ 对照实验中关闭整套增量战术扩展；
`vcf_node_limit` 和 `vcf_max_plies` 调整局部预算。网页不增加实现参数菜单。
搜索统计记录 VCF 工作量、胜法次数及预算未知次数。

普通 Alpha-Beta 仍采用邻近两格、前 16 个安静候选着；没有 VCT 或完备防守搜索。
VCF 的单条证明与整个选择性搜索的最终 mate 分数含义不同：后者仍可能受候选着
截断和搜索边界影响，不代表已解决整盘五子棋。

## 必要回归

`engine/tests/test_vcf.cpp` 用独立连线计数校验增量特征，覆盖 15/20 路、两种规则、
落子/撤销、五手连续冲四、反先成五、深度/节点耗尽和异常恢复。
同一测试编译为原生和 WASM；搜索参考检查比较 PVS/TT 与全窗口路径。
真实 NNUE 的固定参考向量检查同时验证搜索中断后的累加器恢复。

## 2026-09-21 的实际比较

详细数据、程序/权重摘要、每盘结果和训练指标保存在
[本轮记录](benchmarks/2026-09-21-vcf.json)。同一台开发机、相同八个开局，
每个开局交换黑白，两边每手 300 ms、最大名义深度 8：

- 两边都使用网页现有 `rapfi-calibrated-v1` 权重，新搜索对旧搜索 **15 胜、1 负**。
- 两边都使用新搜索，修复 mate 监督后训练的 `rapfi-mate-v2` 对 v1 **5 胜、2 和、9 负**。
- 两组共 32 盘，全部正常结束，无非法着或协议/进程故障。

因此保留 v1 网页权重，发布共用搜索改进；v2 保留为经过运行时核验的研究候选。
这是八个开局的研发样本，不能外推 Elo、正式比赛成绩或手机上的胜率。

对用户提供的棋谱，Node/WASM 使用同一份 v1 权重：白 F11 后，固定名义深度 2，
旧搜索将黑 G10 评为普通分数 +15；新搜索已给出包含实际五连的胜势变化。
黑 G10 后白方行棋，固定名义深度 1，旧搜索给出普通分数 -15，新搜索已识别 mate。
这体现了战术延伸越过静态评估边界，而不是单纯增加名义层数。

该记录在黑 G10 后已经存在两路杀棋，白 H11 不能同时化解另一方向的攻击。
VCF 的首条胜法不保证最短；名义深度、PV 手数与实际 mate 距离不能混为一谈。
3 秒重放仍显示选择性搜索在更早局面存在局限，不能宣称这次已经达到 Rapfi 棋力。
