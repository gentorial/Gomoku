# `engine` 代码逐文件详解

本文面向第一次阅读本项目 C++ 引擎的开发者。它不复制两千多行源码，而是按“文件 → 类型/函数 → 连续代码段”的粒度解释每段代码为什么存在、输入输出是什么，以及各模块如何协作。源码中的空行、花括号和重复循环不再机械复述。

> 阅读约定：坐标从左上角开始，`x` 向右、`y` 向下；`Move{x, y}` 是一个交叉点。`ply` 表示已经落下的棋子数，也就是半回合数。

## 1. 总体结构

```text
调用者
  │
  ├─ Position ─────────── 棋盘、规则、胜负、候选点、增量哈希
  │      │
  │      └─ Threats ───── 双方的即时成五点和冲四点
  │              │
  │              └─ VCF ─ 连续冲四的强制胜证明
  │
  └─ search() ─────────── 迭代加深 + Negamax + Alpha-Beta/PVS + TT
         │
         ├─ HandcraftedEvaluator ─ 五格窗口启发式
         └─ NnueEvaluator ──────── 增量棋形、卷积、价值头和策略头
```

目录职责如下。

| 目录/文件 | 作用 |
| --- | --- |
| `include/gomoku/*.h` | 对外公开的数据结构和接口 |
| `game/position.cpp` | 五子棋规则与棋盘状态 |
| `search/threats.cpp` | 增量战术特征 |
| `search/vcf.cpp` | VCF 强制胜证明搜索 |
| `search/search.cpp` | 主搜索 |
| `eval/handcrafted.cpp` | 无模型也能运行的基础评估器 |
| `eval/nnue.cpp` | 模型加载、增量 NNUE 推理 |
| `eval/nnue_kernels.*` | 标量、SSE2、WASM SIMD 数值内核 |
| `include/gomoku/profile.h` | 可编译关闭的性能计时器 |
| `bench/` | 原生/WASM 基准入口 |
| `tests/` | 规则、搜索、VCF、NNUE 的回归测试 |

## 2. 棋盘与规则：`position.h`、`position.cpp`

### 2.1 基础类型

- `enum class Color : uint8_t { empty, black, white }`：格子状态。数值分别为 0、1、2；NNUE 的棋形编码依赖黑白恰好为 1 和 2。
- `enum class Rule { freestyle, standard }`：`freestyle` 是五个或更多都胜；`standard` 只允许恰好五个，长连不胜。
- `Move`：坐标值对象。默认 `operator==` 让两个坐标可以直接比较。
- `Stone`：把坐标和颜色绑在一起，用于一次性重建局面。
- `opposite`：返回另一方；传入 `empty` 是调用错误，因此抛异常。
- `parse_rule` / `rule_name` / `color_name`：协议字符串和内部枚举之间的边界转换。

### 2.2 `Position` 保存的状态

| 字段 | 含义 |
| --- | --- |
| `size_` | 棋盘边长，只接受 15 或 20 |
| `rule_` | 当前胜负规则 |
| `turn_` | 下一手的颜色，默认黑方 |
| `winner_` | 已确定的赢家；`empty` 也可能表示仍在进行或和棋 |
| `ply_` | 已占用格子数 |
| `hash_` | 包含尺寸、规则、棋子和行棋方的局面哈希 |
| `board_` | 长度为 `size²` 的一维棋盘，索引为 `y * size + x` |
| `history_` | 撤销栈；保存最后一步及落子前的赢家 |

构造函数先把“尺寸 + 规则”混入哈希，再校验尺寸并创建空棋盘。这样相同棋子布局在不同尺寸或规则下也不会得到相同哈希。

### 2.3 哈希辅助代码

- `mix` 是 SplitMix64 风格的整数混合函数，把规律性的格子编号打散成 64 位键。
- `stone_key(index, color)` 为每个“格子 × 颜色”生成固定键。
- `turn_key` 代表轮到白方。落子或撤销时用 XOR 切换它。
- 因为 `a ^ b ^ b == a`，同一个棋子的键再 XOR 一次就能精确撤销，无须重扫棋盘。

这不是用于加密的哈希；它用于置换表快速判断两个搜索节点是不是同一局面。

### 2.4 查询函数

- `contains(move)`：做上下左右四个边界判断。
- `at(move)`：越界时抛异常，否则读取一维数组。
- `legal(move)`：游戏未结束、坐标在棋盘内且格子为空时才合法。`&&` 从左到右短路，所以越界坐标不会传给 `at`。
- `full()`：落子数是否等于总格数。
- `terminal()`：已经有人赢或棋盘已满。
- `status()`：把状态转换成协议可用的 `black_win`、`white_win`、`draw` 或 `playing`。

### 2.5 连线和胜负

`directions` 只列 `{横、竖、主对角、副对角}` 四个无向方向。`line_length` 从假定的中心点出发，分别沿方向的正负两端数连续同色棋子，初值 1 代表中心点本身。

`wins(move, color)` 支持两种用途：

1. `move` 已经是该颜色，用于落子后的真实胜负检查；
2. `move` 仍为空，用于搜索前的“假如下这里会不会赢”。

如果点上是对方棋子就立即返回 `false`。四个方向中，自由规则遇到 `length >= 5` 胜，标准规则只在 `length == 5` 时胜。

### 2.6 `play` 与 `undo`

`play(move)` 的顺序很重要：

1. 检查合法性；
2. 将坐标和旧 `winner_` 压栈；
3. 写入当前方棋子；
4. XOR 棋子键和行棋方键；
5. 增加 `ply_`；
6. 检查刚才一手是否获胜；
7. 最后切换行棋方。

`undo()` 完全反向执行：取出历史、把行棋方切回落子者、撤销哈希、清空格子、恢复旧赢家并减少 `ply_`。旧赢家也入栈，是为了让撤销逻辑不依赖重新扫描棋盘。

主搜索大量使用这对函数，因此它们被 `GOMOKU_SCOPE` 计时。发生限时、取消或异常时，搜索的 RAII 对象仍会调用 `undo()`。

### 2.7 `from_stones`

这个工厂函数用于从协议、数据集或测试直接构造任意合法布局，而不是假装按顺序落子。

- 拒绝缺失行棋方、越界棋子、空颜色和重复坐标；
- 直接填棋盘、更新哈希和 `ply_`；
- 白方行棋时额外 XOR `turn_key`；
- 最后扫描传入的棋子检查赢家；
- 若黑白双方同时已经获胜，认为输入局面自相矛盾并抛异常。

它不会推断棋子数与行棋方是否符合真实对局次序，调用者要负责该层语义。

### 2.8 `candidates`

- 终局没有候选点；
- 空棋盘只返回天元，避免首层枚举 225/400 个等价点；
- 其他局面逐格检查，只保留距已有棋子横纵各不超过 2 格的空点。

这里的“附近”是 `5 × 5` 方形，不是欧氏距离。它是一种选择性搜索剪枝，不代表其余空点在规则上不合法。

## 3. 评估器接口与手工评估：`evaluator.h`、`handcrafted.cpp`

### 3.1 生命周期协议

`Evaluator` 是抽象基类。一次搜索必须遵循：

```text
reset(root)
  push(child_1) ... push(child_n)
  evaluate / move_scores
  pop()        ... pop()
```

- `name()`：返回可展示的实现名称。
- `reset(position)`：在根局面重建累加器；无状态评估器可以不实现。
- `push(position, move)`：棋盘已经执行 `move` 后通知增量评估器。
- `pop()`：撤销最近一次增量更新。
- `evaluate(position)`：必须返回“相对于当前行棋方”的分数，正数有利、负数不利。
- `move_scores(position, moves)`：可选策略分数，顺序必须与输入候选点一致；空数组表示不提供策略排序。

虚析构保证通过基类指针销毁 `NnueEvaluator` 时资源能正确释放。

### 3.2 `HandcraftedEvaluator::evaluate`

代码枚举棋盘中所有完整的五格窗口：每个起点、四个方向，若终点越界就跳过。

`weights = {0, 2, 12, 90, 800, 20000}` 表示一个未被对方阻断的窗口中，己方有 0～5 子时的价值。一个窗口同时有黑白棋时不会给任何一方加分；只有黑子则加分，只有白子则减分。

最终把值限制在 `[-50000, 50000]`，确保启发式不会冒充约 `±100000` 的已证明胜负。内部先按黑方视角累计，若轮到白方则取反，从而满足接口的“当前行棋方视角”。

## 4. 增量战术特征：`threats.h`、`threats.cpp`

`Threats` 不评价局面好坏，只精确回答：某个空点是否立即成五，或落下后是否留下至少一个下一手成五点。

### 4.1 固定容量与编码

- 最大棋盘是 `20 × 20 = 400`，所以 `board_` 和 `features_` 固定 400 项。
- 每点四个方向，共 1600 条局部线状态。
- `codes_[line][side]` 同时缓存黑方视角和白方视角。
- 每条线观察中心两侧各 5 格，中心默认是假设落子的空点，不存入编码，因此是 10 位三进制数，共 `3^10 = 59049` 种。
- 三进制数字：0=空，1=己方，2=对方或棋盘边缘。
- `powers` 是 `3^0` 到 `3^9`；`exponent(offset)` 把 `-5..-1, 1..5` 映射到连续的 0..9。

### 4.2 `Tables` 预计算

构造 `Tables` 时穷举 59049 种线型，再分别为自由和标准规则计算三个 bit：

| bit | 值 | 含义 |
| --- | --- | --- |
| 0 | `1` | 中心落子后立即获胜 |
| 1 | `2` | 中心落子后至少有一个成五回复点，即“冲四” |
| 2 | `4` | 至少有两个不同回复点，即双向四 |

循环中的 `start = 1..5` 枚举所有包含中心格 5 的五格窗口。标准规则额外检查窗口两端，排除会形成长连的窗口。`replies` 用位集合记录第二个空点的位置，`x & (x-1)` 用于判断是否不止一个 bit。

`table(rule)` 内的函数局部 `static` 只初始化一次，之后所有 `Threats` 实例共享只读查找表。

### 4.3 构造与刷新

构造函数先复制 `Position` 棋盘。随后对每个空点、每个方向、两种己方视角编码附近十格；越界按对方/阻挡处理。每条方向编码完成后调用 `refresh`。

`refresh(point, direction)`：

1. 若中心不是空点，该点不可能作为候选，整条特征清零；
2. 否则查黑方编码，把 3 bit 放在低半字节；查白方编码，把 3 bit 左移 4 位；
3. 汇总该点四个方向：任一方向能胜即是胜点；各方向回复数累加后判断是否为四和多重四；
4. 比较新旧特征，增量修正 `wins_`、`fours_` 总数；
5. 把双方特征重新打包进一个字节。

总数缓存让搜索能用 O(1) 判断“当前是否必须进攻/防守”，只有真正取走法列表时才遍历棋盘。

### 4.4 增量 `change`

落一颗棋只会影响穿过该点、距离不超过 5 的中心候选：

- `sign > 0` 写入棋子并把对应三进制位加到编码；
- `sign < 0` 清空棋子并减去同一位；
- 对棋子同色视角加数字 1，对另一方视角加数字 2；
- 每次编码变化后 `refresh` 相关中心点。

`play` 和 `undo` 只是 `change` 的薄封装。`undo` 在清空前从 `board_` 读取被撤销棋子的颜色。

`wins` / `four` 用位掩码 O(1) 查询单点；`winning_moves` / `four_moves` 扫描 `features_` 返回所有匹配坐标。

## 5. VCF：`vcf.h`、`vcf.cpp`

VCF（Victory by Continuous Fours）只证明“进攻方可以连续冲四直到成五”，不是完整的五子棋求解器。

### 5.1 结果语义

- `win`：在给定预算内找到完整强制胜着序列。
- `no_win`：已枚举范围内不存在连续冲四胜；不代表局面必败或必和。
- `unknown`：节点或深度用尽，不能下结论。
- `VcfLimits`：默认最多 32 个半回合、1024 个攻击节点。
- `pv`：证明线；`nodes`：实际访问的攻击节点数。

### 5.2 RAII 落子器 `Played`

构造时先记住落子颜色，再依次更新 `Position` 和 `Threats`；析构时反向撤销。递归正常返回、`continue`、节点耗尽或回调抛异常都会自动恢复两份状态。

### 5.3 `Solver::attack`

函数始终从“当前行棋方就是本层攻击者”的视角工作：

1. 节点或剩余深度不足，返回 `unknown`；
2. 调用 `visit`，让外层搜索检查时间/取消并计入全局节点；
3. 终局无法再开始新 VCF，返回 `no_win`；
4. 己方已有立即成五点，PV 只需该点，返回 `win`；
5. 对手有两个以上成五点，一手挡不完，返回 `no_win`；
6. 对手恰有一个成五点时，候选只能是该防守点；否则枚举己方全部冲四点；
7. 再用 `t.four(move, self)` 过滤，保证被迫防守的一手同时延续己方进攻；
8. 试下攻击手后，若对方有反先成五点，该攻击失败；
9. 取攻击方下一手的成五点，这些就是对手的被迫防守位置；
10. 两个以上成五点构成双杀，PV 加入攻击手和两个终结点即可证明胜；
11. 恰好一个时，替对手下唯一防守，再递归寻找下一次冲四；
12. 任一分支证明成功就拼接 PV；没有成功但至少一个分支预算不足则返回 `unknown`。

这里 `left - 2` 是因为一次递归已经消耗“攻击手 + 防守手”两个半回合。

`solve_vcf` 校验深度在 1..400，创建一次性 `Solver`，然后把状态、PV 和节点数打包返回。

## 6. 主搜索接口：`search.h`

### 6.1 输入

- `SearchLimits.time_ms`：墙钟时间限制，默认 300ms；0 表示立即停止。
- `max_depth`：迭代加深的名义深度，范围 1..64。
- `max_nodes`：0 表示不限，否则主搜索与 VCF 合计不得超过该数。
- `cancelled`：调用者跨线程设置的原子取消标志。
- `observer`：每完成一层迭代就收到一次稳定结果。

`SearchOptions` 可分别关闭置换表、PVS、VCF，便于用慢但简单的参考路径验证优化正确性。置换表默认 `2^18` 项，每项 16 字节，即 4 MiB。

### 6.2 输出

- `best_move`：最佳着；即使零时间也尽量提供合法 fallback。
- `score`：当前行棋方视角分数，接近 `+100000` 表示已证明获胜。
- `depth`：最后完整完成的迭代深度。
- `nodes` / `elapsed_ms`：工作量和耗时。
- `pv`：Principal Variation，最佳变化线。
- `reason`：`completed`、`terminal`、`cancelled` 或 `limit`。
- `stats`：TT、PVS、评估器和 VCF 的诊断计数。

## 7. 主搜索实现：`search.cpp`

### 7.1 常量、分数和置换表

- `mate = 100000`：已证明胜负的基准分；普通评估必须远离它。
- `infinity = mate + 1`：Alpha-Beta 初始边界。
- `Interrupted`：内部控制流异常，用来同时跳出多层递归。
- `Bound::exact/lower/upper`：TT 项分别是精确值、下界、上界。
- `Entry` 固定 16 字节：64 位键、32 位分数、16 位走法、8 位深度和 8 位边界类型。

Mate 分数包含距根节点的 `ply`，例如越快获胜分越高。TT 项可能在另一搜索深度复用，因此 `to_table` 把根相对距离转成节点相对距离，`from_table` 再转回来。普通启发式分数原样保存。

走法压成 `y * 20 + x`，因为最大边长固定为 20；读取时用 `% 20` 和 `/ 20` 还原。

### 7.2 两个 RAII 守卫

- 搜索版 `Played`：构造时 `Position::play`，若启用战术特征也 `Threats::play`；析构时成对撤销。
- `Accumulated`：进入需要评估的子节点时调用 `Evaluator::push`，离开时 `pop`。

二者禁止复制，避免同一落子被撤销两次。它们是“超时/取消/评估器异常后状态仍平衡”的核心保证。

### 7.3 `Search` 会话对象

它持有本次搜索专属的评估器引用、限制、取消标志、起始时间、节点计数、统计、TT，以及可选 `Threats`。TT 不跨搜索共享，因此换模型后不会读到旧模型的分数。

`check()` 检查三类中断：原子取消、时间到达、非零节点预算耗尽。原子读取使用 `memory_order_relaxed`，因为这里只需要看到一个布尔信号，不承担其他内存同步。

### 7.4 TT 的 `probe` 与 `store`

- 表大小必须是 2 的幂，所以 `key & (size - 1)` 等价于更慢的取模。
- `probe` 只有槽位非空且完整 64 位键相同时才命中；碰撞不会被误认。
- `store` 使用深度优先替换：已有项搜索更深时，不用浅结果覆盖。
- `store` 同时记录最佳走法，即便分数边界不能直接剪枝，也可优先尝试这一步。

### 7.5 候选排序 `ordered`

排序顺序如下：

1. 若己方有即时成五，只返回所有成五点；
2. 否则若对方有即时成五，只返回所有必防点；
3. 从 `Position::candidates()` 得到邻近空点；
4. 一次性向评估器请求 policy 分数；
5. `priority=3` 表示己方成五，`2` 表示挡住对手成五，`0` 表示安静着；
6. 几何启发式奖励附近已有棋子，惩罚远离中心；
7. 按战术优先级、policy、几何分、原始顺序稳定地比较；
8. `partial_sort` 只排需要的前部；保留前 16 手以及全部即时胜/防点。

最终搜索仍是选择性的：普通候选只取 16 个。policy 只改变次序，不允许丢掉即时战术点。

### 7.6 延迟生成 `Picker`

`Picker` 先返回 TT 或上一层 PV 推荐的 `preferred` 走法，只有它没产生剪枝时才调用昂贵的 policy 与排序。生成完整列表后会跳过已经试过的推荐着。

注释所说“推荐着属于选择集合”，依据是它来自完全相同哈希局面先前已搜索的着法。`preferred_cutoffs` 统计在候选列表尚未生成时就剪枝的次数。

### 7.7 `negamax`

Negamax 利用“对手的最好分数取负，就是我的分数”，把 Minimax 的最大层和最小层统一成一个函数。

执行顺序：

1. 检查预算、增加节点、清空本节点 PV；
2. 若上一手已经获胜，当前方输，返回 `-mate + ply`；和棋返回 0；
3. 用 `Threats` 直接识别己方一步胜、对手双成五必胜以及单点强制防守；
4. 到达名义叶节点且不是强制防守时，若己方有冲四，尝试有预算的 VCF；
5. 查询 TT，读取推荐着；若深度和边界满足条件则直接返回；
6. 只有没被终局/TT 截断的节点才 `Evaluator::push`，避免无用 NNUE 更新；
7. 真正的安静叶节点调用 `evaluate` 并存精确 TT；
8. 依次取候选着，执行棋盘/战术状态，再递归搜索子节点；
9. 第一个孩子用完整窗口，后续孩子在 PVS 模式先用 `[-alpha-1, -alpha]` 零窗口试探；只有落在 `(alpha, beta)` 内才完整重搜；
10. 更优分支替换 `best`、`best_move` 和 PV；
11. 更新 `alpha`，若 `alpha >= beta` 则 Beta 剪枝；
12. 根据结果相对原窗口的位置，把 TT 项存成 lower、upper 或 exact。

`child_depth = max(depth - 1, 0)` 配合 `forced` 实现强制防守延伸：名义深度到 0 时，只要还必须挡对手唯一成五点，就继续下，不让评估器把必输局误当安静局面。

TT 截断条件对完整窗口更谨慎：强制延伸节点要保留可解释 PV；零窗口本来只询问一个边界，可以安全复用相应 bound。

### 7.8 顶层 `search`

1. 校验限制、TT 大小和 VCF 深度；
2. 创建搜索会话并 `evaluator.reset(root)`；
3. 根局面已结束时直接返回 `terminal`；
4. 先准备合法 fallback，再优先把它替换为即时防守或即时获胜；
5. 用评估器给根局面一个初始分数；
6. 复制根 `Position`，保证调用者对象绝不被修改；
7. 从深度 1 到 `max_depth` 迭代加深；上一轮最佳着成为下一轮首选；
8. 每完整完成一层，原子式更新结果并调用 observer；未完成的半层不会污染最终答案；
9. 找到 mate 范围结果后提前结束；
10. 捕获 `Interrupted`，区分显式取消和普通限制；
11. 无论如何更新最终节点、耗时和统计。

根节点没有有限 `beta`，因此 PVS 后续着只需在超过当前 `alpha` 时用完整根窗口重搜。

## 8. NNUE 公开接口：`nnue.h`

`NnueModel` 是经过完整校验后不可变的权重对象，以 `shared_ptr<const ...>` 在多个搜索会话之间共享。它保存通道数、价值头/策略头宽度、适用棋盘与规则、原始字节数，以及 14 个 `int16` 张量。

- `max_bytes = 512 MiB` 防止恶意或损坏文件导致无限分配。
- `load(bytes)` 从内存加载，适合 WASM。
- `load_file(path)` 适合原生程序。
- `supports(position)` 要求棋盘尺寸和规则都匹配训练模型。

`NnueEvaluator` 用 Pimpl（私有 `State` + `unique_ptr`）隐藏大量实现细节，也避免头文件暴露内部容器。它实现评估器生命周期，并额外公开三分类价值 logits 供一致性测试。

## 9. NNUE 模型加载：`nnue.cpp` 前半

### 9.1 数值辅助

- `patterns = 397488`：所有带不同边界长度的 11 格线型码总数。
- `aligned(features)`：给网络输入附加 2 个元特征后向上补齐到 16，便于 SIMD。
- `rounded(value, denominator)`：实现 floor 基础上的 ties-to-even（银行家舍入），并显式修正 C++ 负数除法向零截断的问题。
- `activate`：除以量化尺度 1024、ties-to-even，再截断到 `[0, 256]`。

### 9.2 `Reader`

`Reader` 用 `span<uint8_t>` 和偏移量顺序读取二进制：

- `take(n)` 先检查剩余长度，防止越界；
- `u32()` 按小端序组合 4 字节；
- `expect(v)` 用于魔数后的版本号、张量形状和量化尺度校验；
- `width()` 限制网络宽度为 1..1024。

### 9.3 `NnueModel::load`

加载过程故意“先验证结构，再分配大张量”：

1. 检查总文件上限和 8 字节魔数 `GMLINE1\0`；
2. 检查格式版本、网络版本，读取已折叠的 mapping 宽度；
3. 读取通道、价值隐藏层、策略隐藏层宽度及量化常量；
4. 检查棋盘只能 15/20，规则只能 0/1；
5. 检查固定 14 个张量和 397488 种 pattern；
6. 在 `shapes` 中按网络结构计算每个张量预期形状；
7. 先算出整个文件的精确预期字节数，不相等立即拒绝；
8. 对每个张量检查 32 字节名称、维数、量化尺度、四维形状；
9. 把小端有符号 16 位数手工解码，避免平台端序和未对齐读取问题；
10. codebook 权重限制在 ±256，其他权重限制在 ±8192；
11. 保存实际字节数并返回只读模型。

14 个张量依次组成：横竖/对角 codebook、深度可分空间卷积、价值隐藏层和输出层、策略局部层、策略全局层和策略输出层；每个 weight 后紧跟 bias。

`load_file` 先在文件尾取得长度，校验后一次读取，再复用 `load`，因此内存与文件加载的格式验证完全一致。

## 10. NNUE 增量状态：`NnueEvaluator::State`

### 10.1 主要结构

- `Line`：某点某方向的有效棋盘格列表，以及该边界长度组合在 codebook 中的基址。
- `LineChange`：某次落子会修改哪个中心点、哪个方向和哪一位三进制权重。
- `Neighbor`：卷积输入会扇出到哪个输出点、使用 3×3 的哪个 kernel tap。
- `Affected`：某点落子后，要重算的 merged 点、spatial 点和棋形码。
- `Frame`：一次 `push` 前保存的局部缓存、池化和旧哈希，用于精确 `pop`。

主要张量缓存：

| 缓存 | 含义 |
| --- | --- |
| `pattern_ids` | 每点、双方视角、四方向的 codebook 索引 |
| `merged` | 四方向 codebook 向量求和并激活后的特征 |
| `deltas` / `changed` | 新旧 merged 差和是否变化 |
| `preactivation` | 3×3 depthwise 卷积激活前的整数值 |
| `spatial` | 激活后的空间特征 |
| `pools` | 双方 ×（全局 + 9 宫格）× 通道的和 |
| `frames` | 搜索深度对应的撤销帧，容量复用 |
| `*_input/hidden/output` | 价值头和策略头反复使用的 scratch buffer |

所有关键特征都保存黑、白两种绝对视角；真正送入网络时再按当前行棋方排列为“自己、对手”。

### 10.2 构造函数的预计算

1. 把训练张量的卷积布局重排成 `kernel × channel`，便于增量内核连续读取；
2. 为左右各 0..5 的边界长度组合计算不同三进制串在总 codebook 中的起始 offset；
3. 把棋盘分成 3×3 区域，0 号池是全局，1..9 是区域池；20 路不能均分时使用 floor 边界公式；
4. 为每点四个方向列出半径 5 内的有效格；
5. 预计算某点落子会影响哪些 line-merge 点，以及这些点外扩 1 格后的卷积 halo；
6. 预计算每个卷积输入向哪些输出扇出及对应翻转后的 kernel 索引；
7. 反向建立 `affected[cell].lines`，让落子能直接修改所有相关 pattern id。

这些工作只在创建评估器时进行，搜索节点内不再做几何关系计算。

### 10.3 棋形更新

- `check(position)`：确认评估器已 reset、哈希一致且模型兼容，捕获错误的 push/pop 顺序。
- `rebuild_patterns(position, point)`：全量读取一条线上每格，黑视角用黑=1/白=2，白视角反转；加上边界长度 offset。
- `change_patterns(point, color, sign)`：落子/撤销时只对预计算关联项加减 `digit * power`。
- `update_merged(point)`：从横、竖 codebook 和两条对角 codebook 取四个向量，求和、截断，并保存 delta。
- `propagate(point, incremental)`：把 merged 全值或增量通过 depthwise 3×3 卷积扇出到相邻 preactivation；增量模式跳过未变化点。
- `update_spatial(point)`：激活卷积输出，并用新旧差同时维护全局池与所属区域池。
- `copy_points`：在 Frame 与活动缓存间保存/恢复指定点，模板同时支持 int16 和 int32。

### 10.4 网络输入和全连接层

`input(value, result)`：

- 价值头使用 10 组池（全局 + 九宫格），策略全局头只使用全局池；
- 每组先放当前行棋方视角，再放对手视角；
- 池和除以区域面积并 ties-to-even，得到平均特征；
- 附加“是否黑方行棋”和“棋盘尺寸/20”两个缩放到 0..256 的元特征。

`linear(tensor, values, result)` 对每个输出行计算 `bias * 256 + dot(weight, input)`，使用 64 位结果避免长向量求和溢出。tensor 编号也用于选择性能计时阶段。

## 11. NNUE 生命周期与输出：`nnue.cpp` 后半

### 11.1 构造、`reset`、`push`、`pop`

- 构造函数拒绝空模型并创建 State。
- `reset` 验证模型，记录行棋方和哈希，清空深度/池；全量重建所有 pattern 和 merged，再以 bias 初始化卷积 preactivation，传播所有点并激活池化。
- `push` 的参数是“已经落完子的 Position”。它验证行棋方确实已切换、落点上是旧行棋方棋子；保存受影响区域和整个小型 pools；增量更新棋形、卷积和池；最后增加深度并接收新哈希/行棋方。
- `pop` 恢复 Frame 保存的 merged、spatial、preactivation 和 pools；从 pattern id 减去被撤棋子；恢复哈希并切回行棋方。

Frame 数组按最大达到过的搜索深度复用，避免每个节点反复分配容器对象。

### 11.2 价值头

`value_logits` 校验状态，生成 20 组池特征的输入，依次执行隐藏全连接、量化激活、三分类输出，最后除以 `262144 = 256 × 1024` 还原为浮点 logits，顺序是胜、和、负。

`evaluate` 使用减去最大 logit 的 softmax 技巧避免 `exp` 溢出。先求 `P(win)-P(loss)`，再通过 `600 * atanh(...)` 转成无界但夹紧的搜索评估单位。反变换 `tanh(score/600)` 可以恢复这一概率差。它不是 Elo，也不是 mate 距离。

### 11.3 策略头

`move_scores` 先算一次全局策略向量。对每个候选点：

1. 越界抛异常；已占用点给 `-1e9`；
2. 取该点当前方/对手的 spatial 特征拼成 `paired`；
3. 计算局部策略隐藏向量；
4. 与全局隐藏向量逐项相加后激活；
5. 通过单输出层得到该点 logit。

返回的是未归一化 logits；搜索只比较大小，无需做 softmax。

## 12. SIMD 数值内核：`nnue_kernels.h`、`nnue_kernels.cpp`

编译时优先选择 WASM SIMD128，其次 SSE2，否则执行完全等价的标量尾循环。所有函数都支持任意 `count`，不要求是 8 的倍数。

### 12.1 `dot`

计算两个 int16 向量的 64 位点积。SIMD 每次处理 8 项，但每最多 256 项就把四个 int32 lane 汇入 int64，防止 lane 长时间累加溢出。余数由标量循环处理。

### 12.2 `merge`

逐通道计算 `clip(a+b+c+d, 0, 256)`，同时写出相对旧 output 的 `delta`，并返回是否有任何通道变化。WASM 用 `any_true`，SSE2 用等于零的字节 mask 判断变化。

### 12.3 `accumulate`

执行 `output += delta * weight`。WASM 可直接扩宽乘法；SSE2 分别取 16 位乘积高低半部，再交错还原成有符号 32 位乘积。

### 12.4 `activate_pool`

把 int32 preactivation 除以 1024、ties-to-even、截断到 `[0,256]`，写回 int16 激活；再用新旧激活差同时更新全局池和区域池。

`511 + ((x >> 10) & 1)` 是 ties-to-even 的整数实现：恰在半点时根据商的奇偶决定是否进位。C++20 有符号右移按 floor 方向工作，因此负边界也与参考实现一致。

## 13. 性能采样：`profile.h`

`Phase` 枚举列出所有可测阶段，`names` 必须与枚举顺序一一对应。`Event` 记录调用数、包含子调用的 inclusive 时间、扣除子调用的 exclusive 时间。

定义 `GOMOKU_PROFILE` 时：

- `current` 和 `top` 是 `thread_local`，各线程独立记录；
- `Session` 临时安装 Recorder，析构时恢复先前会话；
- `Scope` 构造时入栈并记时，析构时累加自身时间，把总耗时记入父级的 `children_ms_`；
- 两个宏用 `__LINE__` 生成不重名的局部 Scope 变量。

未定义该宏时，`Session` 和计时宏为空操作，生产构建不支付读时钟成本。

## 14. 评估器说明：`eval/README.md`

这个短文件不是实现代码，而是评估器扩展契约的维护说明。它强调 `reset → push/evaluate/pop` 的配对顺序、手工评估器与 NNUE 的边界、权重只在搜索前解析，以及增量更新必须和全量重建逐值等价。新增评估器或修改 NNUE 生命周期时，应同时满足这里列出的约束和相应回归测试。

## 15. 基准程序：`bench/benchmark.cpp`

全局只读 `model` 在多次请求间复用。

- `position_from_case` 同时支持普通协议局面和二维整数棋盘；严格检查行列尺寸与格子值 0..2。
- `benchmark` 检查模型、深度、节点和时间参数，创建 profile 会话、局面和 `NnueEvaluator`，再调用主搜索。
- `observe=true` 时 observer 记录每层完成时的深度、节点与墙钟时间。
- 返回 JSON 包含最终分析、阶段计时、每层迭代和 TT/PVS 等统计。

WASM 构建导出两个 C ABI 函数：

- `gomoku_bench_load_model(bytes, size)`：从 JavaScript 内存加载模型；返回空字符串表示成功，否则返回错误文本。
- `gomoku_bench(input)`：解析 JSON 请求并返回 JSON 结果或 `{error}`。

两者用静态字符串保存返回值，保证函数返回后 `c_str()` 仍有效，但下一次调用会覆盖它。

原生 `main` 要求唯一参数是权重路径；加载后输出 ready JSON，再从标准输入逐行读取 JSON、逐行输出结果，便于脚本保持一个热进程反复测量。

- `ladder` 创建固定五手 VCF 阶梯；`verify_proof` 验证每个防守确实唯一、双杀只出现在证明末尾，最终真实成五。
- 随机走子/撤销覆盖 15/20 路与两种规则，周期性全盘验证增量特征。
- 检查正常证明、深度耗尽、零节点预算、回调异常后的完整恢复。
- 把 VCF 嵌入深度 1 主搜索，确认能读出五手胜法和正确 mate 分数。
- 检查全局节点预算也约束 VCF。
- 检查对手反先成五优先于己方冲四。
- 检查自由/标准规则对“中间补成长连”的不同判定。
- 最后一段是真实用户棋谱回归：必须走唯一防守 G10，并证明随后两个分支都能 VCF 获胜。

### 17.4 `test_nnue_kernels.cpp`

对许多边界长度（含小于 SIMD 宽度、刚好/超过 8、256 分块边缘和很长向量）比较 SIMD 与标量数学结果：

- 最大正负权重下点积不溢出；
- merge 的截断、delta 和“不变时返回 false”正确；
- 卷积增量包含负数时正确；
- 在 ±0.5、截断边缘和极值处与 `nearbyint` 的 ties-to-even 一致；
- 全局池和区域池都只增加激活差。

### 17.5 `nnue_check.cpp`

这是带真实模型与 JSON 参考向量的验收程序，不是普通无资源单测：

1. 加载 `.gnn` 和 `line-nnue-reference-v1`；
2. 从棋盘矩阵或走子序列构造局面；
3. 对所有棋盘点逐值比较 C++ 的 value/policy logits 与参考数据，要求零误差；
4. 随机走最多 12 手，每手比较增量 evaluator 与全量 `reset` evaluator；
5. 逐手撤销并继续比较；
6. 运行受节点限制的搜索，再确认中断没有污染根累加器；
7. 输出检查数量和 `maxAbsoluteError: 0` 的 JSON。

## 18. 一次搜索的完整状态时序

```text
search(root)
  evaluator.reset(root)
  Threats(root)
  for depth = 1..N
    for root move
      Played: Position.play + Threats.play
      negamax(child)
        终局/TT 命中？直接返回，不更新 NNUE
        Accumulated: evaluator.push(child, last_move)
        叶节点？evaluate(child)
        否则继续 Played + negamax
        Accumulated 析构: evaluator.pop
      Played 析构: Threats.undo + Position.undo
    完整一层结果交给 observer
  返回最后完整一层
```

必须长期保持的三个不变量是：

1. `Position.hash()` 精确描述当前棋盘、规则、尺寸和行棋方；
2. `Threats` 与 `Position` 表示同一棋盘；
3. `Evaluator` 的累加器栈顶与当前 `Position.hash()` 一致。

项目中大量 RAII 和测试，最终都是为了在正常返回、剪枝、超时、取消和异常五种退出路径下同时守住这三个不变量。

## 19. 推荐阅读顺序

如果准备修改引擎，建议按以下顺序读源码：

1. `position.h` → `position.cpp`：先掌握状态和规则；
2. `evaluator.h` → `handcrafted.cpp`：理解搜索要求的评估器契约；
3. `search.h` → `search.cpp`：掌握主控制流；
4. `threats.h/.cpp` → `vcf.h/.cpp`：理解强制战术；
5. `nnue_kernels.*` → `nnue.cpp`：最后进入量化和增量网络；
6. 对照各测试阅读，确认每个优化必须保持哪些外部行为。
