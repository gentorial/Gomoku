# NNUE 正式架构

状态：正式训练框架、真实 Rapfi 蒸馏训练、原生/WASM NNUE 增量推理均已接通。
当前网页默认使用已验收的 `rapfi-calibrated-v1`；对战棋力认证与模型晋级仍待完成。
已接通 `line11-dual-v1` 网络、数据分片、混合监督、单设备训练与恢复、量化导出和整数参考。
可运行命令见 [训练框架](../training/README.md)，准确算子与二进制规范见
[line11 格式](../models/line11-format.md)。下文同时包含已实现规范和后续研发目标；
已接通官方 Rapfi 教师进程和固定版本 binpack；多卡 DDP、原生增量推理及模型晋级尚未完成。

本设计落实的开发方向是：直接建设长期使用的网络、数据管线和运行时，
在同一套正式实现上完成验证与规模训练。停止扩建过渡用的小型 MLP。
训练设备与网络架构分离：支持 CPU、受支持的 Intel GPU（XPU）与 NVIDIA GPU（CUDA）。
开发机不要求配备 NVIDIA；训练可在本机或远程机器执行，数据与训练状态考虑多卡扩展。

## 稳定边界与可配置参数

优先固定局面语义、特征编码、网络算子、标签类型、模型兼容性和推理数值规范。
在这些约束内，通道宽度、批量大小、数据量、训练步数、标签权重和工作进程数可配置。
扩大数据量不改变数据语义；调整宽度需要重新训练和导出，但不重写数据管线、
协议适配器或网络算子。已有检查点不保证能够直接恢复到不同宽度的网络。

架构族确定后，具体布局与数值规范仍须通过资源测量和跨语言校验才能冻结为 v1。
研究中如果确实需要改变特征或算子，应发布新的架构版本，并保留原始数据和旧产物。
接口稳定不等于承诺网络永远不需要修改。

## 网络结构

正式网络采用局部棋形映射、特征增量更新、价值与着法双头的结构族。
设计参考 [Rapfi / MixNet 论文](https://arxiv.org/html/2503.13178v1) 中的
四方向棋形映射和增量特征图；本仓库的模型格式不承诺直接兼容 Rapfi 权重。

数据流如下：

    棋盘、规则、行棋方
        → 四方向局部线形编码
        → 可导出为查找表的共享映射网络
        → 方向特征聚合与局部空间交互
        → 全局及区域特征汇总
        → value：局面价值
        → policy：候选着排序

### 特征与映射

- 首个正式特征版本使用长度 11 的线段，覆盖横、竖和两条斜线。
  边界位置与空位必须可区分，不能把棋盘外填成可落子的空位。
- 输入保留实际棋盘尺寸、绝对执棋颜色与行棋方。相对颜色视角的转换必须明确，
  后续支持颜色不对称的规则时不能丢失黑白身份。
- 训练端用共享参数的方向映射网络提取棋形特征，导出端枚举可编码的线形，
  生成运行时查找表。映射网络的训练计算量与引擎查表成本分开记录。
- 推理会话维护黑白两种视角的特征状态，落子局部更新两者；换手时选择对应视角，
  避免仅因行棋方改变就重算整盘特征。
- 方向聚合后使用有界局部空间算子，首版选择 3×3 depthwise 卷积。
  影响范围可计算，走子和撤销只更新受影响位置及其汇总量。

映射权重的方向共享方式、边界索引顺序、区域划分方式及激活位置属于架构规范。
它们必须先写入可执行特征规范与固定测试向量，不能由训练端和 C++ 分别猜测。

### 价值与着法输出

- value 头从正式版本起输出胜、和、负三个 logits，视角固定为当前行棋方。
  训练中可计算概率；搜索端按版本化转换规则取得有界整数分值。
  网络分值与终局、已证明杀棋的分值使用不同区间。
- policy 头结合局部特征与全局上下文，为合法候选着提供排序分数。
  只在需要排序的节点调用，叶节点评价不强制生成全盘着法概率。
- policy 参与排序；合法性、即时获胜和必要防守由规则与战术搜索负责。
  不能仅凭低 policy 分数排除必须搜索的防守着。
- 通道数和头部宽度由正式模型配置确定，导出文件携带准确结构标识。
  网页与比赛程序实现同一套算子，优先验证同一份权重在两端运行。
  后续若确需不同资源档位，也沿用同一结构族和产物规范。

架构的资源预算同时包含映射查找表、两个视角的特征缓存、撤销记录和搜索缓存。
不能只用训练参数量或压缩后的下载大小代表部署内存。

## 数据与老师适配

数据按千万至亿级局面的存储、流式读取和可恢复生成需求设计。
这是容量设计目标，实际生成量与训练预算由任务配置决定。
训练读取器不把完整棋局集或展开后的所有浮点特征一次性装入内存。

保留三层可追溯产物：

1. 原始棋局与局面：棋局编号、开局组、规则、尺寸、执棋方、落子与结果来源。
2. 标注：局面标识、老师程序及权重摘要、搜索预算与实际完成信息、原始评分、
   评分类型和视角、可选 WDL、可选着法信息，以及失败或不完整原因。
3. 训练数据集：不可变 manifest、分片及校验和、数据处理版本、归一化配置、
   采样与划分规则、来源清单。

原始标注和训练目标分开保存。改变混合权重、归一化温度或采样比例时，
应能复用原始标注，避免重新调用老师。局面与标签不绑定某个网络宽度。

首个老师适配官方 Rapfi 250615 自带的 selfplay 模式与未压缩 binpack，
程序、配置和网络均固定摘要，启动时验证 NNUE 真实加载。
导入时验证记录是否实际含有评分，区分普通评分、杀棋与缺失值，
完整棋局交由 C++ 规则核验。命令及准确标签尺度见 [教师工具](../tools/README.md)。
以后接入 KataGomo 或自己的引擎时，实现相同的标注接口。
Gomocup 能返回落点并不代表能返回完整分析；现有 Pbrain 客户端尚未采集老师评分。

生成任务以分片为工作单位，拥有明确任务编号和配置摘要；
当前官方教师只能从时钟播种，采集器错开启动并保存原始数据，不承诺重新生成逐盘一致。
完成分片通过校验后原子发布，失败任务可以恢复，避免重试重复写入同一批样本。
单机先使用进程工作池和文件清单，不需要先引入外部队列服务。

训练、验证、测试按棋局和开局组隔离；还需要处理跨组重复局面以及旋转、镜像等价局面。
几何增强只在划分确定后进行。保持开局、阶段、优势程度和来源的可配置采样，
排除由超时、协议故障或非法落子判负产生的结果标签。

不同规则独立分区。首个运行时覆盖现有规则库支持的 freestyle 与 standard，
模型按规则发布，允许声明多个经过训练和验证的棋盘尺寸。
一份模型不能仅因运行时支持 15×15 和 20×20 就声称两者都具备有效棋力。
Renju 等规则要先补足规则库和输入语义，再声明模型支持。

## 监督信号与训练

固定标签的类型与视角，混合比例保留为配置。

- 结果标签：当前行棋方的胜、和、负类别；没有可靠结果时使用缺失标记。
- 老师 WDL：保留三个概率，可用软标签交叉熵。
- 老师标量：保存原始分数与经校准的归一化值，用模型的
  `p(win) - p(loss)` 学习该标量；不能从一个标量凭空恢复三个 WDL 概率。
- 杀棋或界限评分：单独标记；不作为普通无界数值做均方回归。
- policy：区分访问次数分布、MultiPV 评分、排序与单一最佳着。
  由评分构造的分布要记录转换方式，单一最佳着不能伪装成完整搜索分布。

总损失组合可用的老师价值、最终结果和 policy 监督，并记录每类有效样本数。
缺失标签通过掩码处理；不能把缺失结果当作和棋、缺失评分当作零分。
损失权重与采样策略通过验证集和对战选择，不能宣称某个固定比例始终最优。

正式训练器从开始就包含：

- 设备可配置的单机训练，流式分片读取、可配置预取和受限的主存使用。
- 训练配置与数据清单快照、日志、独立验证集、最佳与最近检查点。
- 恢复模型、优化器、调度器、随机数及采样进度；恢复检查兼容性。
- 量化感知的算子约束，训练与导出共用结构配置。
- 多卡所需的分片采样与同步边界。增加设备时显式处理有效批量与学习率，
  不承诺改变设备数量后逐步数值或样本顺序仍与原运行完全一致。

现有 MLP 训练入口已被正式训练器替换。棋谱校验、原生规则复用和工具测试继续保留。
当前读取为同步 mmap、有界块打乱与梯度累积；可配置预取和 DDP 是后续执行层工作。

### 训练设备与运行位置

CPU、XPU 和 CUDA 执行同一份正式网络与数据管线。网络和损失优先使用标准
PyTorch 算子，避免把 CUDA 专用扩展变成必要依赖。设备选择、混合精度、同步计时、
内存统计和分布式通信属于训练运行层，不进入模型语义或导出权重格式。

- CPU：始终保留可执行路径，用于开发、数值校验，也可以训练；大规模任务是否
  值得在 CPU 上执行，应由完整训练步骤的吞吐决定。
- Intel XPU：作为无 NVIDIA 开发机的本地 GPU 路径。PyTorch 官方列出
  Windows 11 上的 Core Ultra Series 3 / Panther Lake，并提供训练支持；
  仍需验证所选 PyTorch 版本、驱动与正式网络的前向、反向及优化器步骤。
  参考 [PyTorch Intel GPU 指南](https://github.com/pytorch/pytorch/blob/main/docs/source/notes/get_start_xpu.md)。
- NVIDIA CUDA：作为另一种训练后端，可运行于本地或远程 GPU 主机。
  使用远程训练不改变网页和比赛程序的 CPU/WASM 推理路径。

CPU、XPU 与 CUDA 的依赖环境分别固定版本；不要求一套 Python 环境同时装入
互不兼容的后端发行包。显式指定但不可用的设备应给出错误，不能静默回退 CPU
后让大任务运行速度远低于预期。混合精度及算子支持按实际后端验证。

远程任务使用相同源码版本、训练配置和数据 manifest，通过检查点恢复与同步产物。
检查点的张量加载要支持目标设备映射，不能绑定原机器的 GPU 编号或绝对路径。
跨设备不保证逐位相同训练轨迹，恢复时须验证优化器、精度与配置兼容性。

正式大规模训练之前，用相同正式网络测量本地可用后端的完整训练吞吐和峰值内存。
若本地时间预算不足，可把相同训练任务迁移至远程 GPU；不需要重写模型或重新标注数据。
没有 NVIDIA 不影响本地规则、搜索、Rapfi 标注、数据处理与 C++/WASM 开发。

## 量化、格式与原生推理

为同一个正式网络实现浮点参考、量化参考、原生标量及优化推理。
全量重算实现长期保留，用于验证增量更新，不作为另一套待替换的产品网络。

运行时采用量化的查找表及算子。表项、权重、累加器的整数位宽要依据
实际取值和最坏累加范围确定；仅靠小批样本未出现溢出不能证明安全。
舍入、缩放、截断与饱和语义是格式的一部分。先核对标量参考，再比较
原生 SIMD 和 WASM SIMD 优化实现；不支持 SIMD 的构建保留参考实现。

模型产物包括二进制权重及可读 manifest：格式版本、特征与架构标识、
规则与尺寸支持、维度、量化规范、分块长度与校验、文件摘要、数据清单摘要、
训练和导出配置、源代码版本。格式版本与模型身份分开，结构或权重变化可识别。

加载器在搜索开始前验证所有长度、维度、兼容性和资源上限，拒绝未知或损坏产物。
训练检查点与发布权重使用不同的产物类型；把清单改成 runtimeCompatible=true
不能替代真实的导出、推理与一致性验收。

进程内不可变模型权重可以共享；每个搜索会话拥有独立特征缓存和撤销状态。
模型切换需要隔离或清空旧评估相关缓存。未来置换表必须考虑模型上下文。

## 仓库中的实现归属

下面是正式实现的模块职责，新增文件仍需实现，不以存在目录代替功能完成。

- `tools`：老师进程适配、棋局生成、局面标注、任务分片和对战。
- `training`：数据导入与采样、正式网络、损失、训练与恢复、量化参考及导出。
- `models`：格式与结构规范、发布清单；大权重放发布产物或外部存储。
- `engine/eval`：模型校验与加载、特征编码、全量与增量推理、标量/SIMD 算子。
- `engine/search`：通过评估会话获取价值与可选 policy 排序；继续建设
  置换表、PVS、战术搜索和时间控制。
- `packages/contracts`：入口能查询模型身份与能力；不复制网络或特征计算。
- `packages/engine-wasm` 与 `apps/web`：加载和缓存模型资源，把模型交给 WASM。
- `apps/engine-worker` 与 `apps/gomocup`：原生模型选择及生命周期适配。

HTTP、JSON、Python、老师程序和模型下载逻辑不进入搜索节点循环。
比赛程序在本地加载随发布包提供的权重，网页从静态资源中加载相同格式的权重。
网页缓存应按模型摘要区分；现有取消操作会终止 Worker，正式接入需避免
每次重建 Worker 都重新从网络下载权重，并测量重新加载与内存复制成本。

## 实现与验收顺序

所有阶段都针对上述正式网络，每一项产物继续用于后续训练和发布。

1. 冻结可执行特征、标签与权重规范；确定方向编码、边界、视角、算子顺序、
   量化与最终分值转换，并计算资源预算。
2. 建设数据分片、老师标注、正式网络和量化导出；同时实现 C++ 全量参考、
   增量状态和 WASM 加载。具体编码顺序遵循依赖，不要求一次提交全部模块。
3. 用正式网络与同一数据管线完成数值、取消/撤销、吞吐和内存检查。
   少量输入属于正确性测试；不另写特征、网络或数据格式来做过渡版本。
4. 按正式训练任务生成大规模数据，训练、恢复、导出并记录实验。
5. 在固定开局、交换颜色、相同用时下评测原生和 WASM；通过准入条件后发布。
   自对弈候选模型也必须经过同样评测，不能自动覆盖已发布模型。

长期保留的检查包括：量化参考与 C++/WASM 整数中间结果、浮点与量化误差，
随机合法走子/撤销/取消后的全量与增量一致性、规则及模型不兼容拒绝，
固定战术集、采样与划分完整性、训练恢复、节点吞吐和实际对战。
普通 CI 运行确定性的实现检查；大规模训练和有统计要求的对战单独运行并保存产物。

在正式大规模训练前，还要用目标训练设备和浏览器设备明确通道宽度、
训练显存、下载体积、常驻内存和延迟预算。它们是配置与发布门槛，
不能在没有测量的情况下视为已经达到。
