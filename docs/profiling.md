# 引擎性能测量

`pnpm engine:profile` 构建并运行原生和 Node/WASM 的固定局面基准。
测量使用 `models/web-model.json` 固定的真实模型；先执行 `pnpm model:download` 准备权重。
浏览器测量使用相同的 WASM 构建和测试脚本，在独立 Web Worker 中执行。

## 复现

```sh
pnpm engine:profile
node scripts/profiling/server.mjs
```

在浏览器打开 `http://127.0.0.1:4177/`，点击“开始测量”。浏览器测量完成后执行：

```sh
node scripts/profiling/report.mjs
```

报告位于 `artifacts/profiling/report.html`，也可以访问 `http://127.0.0.1:4177/report.html`。
`native.json`、`wasm.json`、`browser-wasm.json` 保存原始样本；`summary.json` 和 `phases.csv`
保存汇总及逐阶段数据。报告完全离线，嵌入本次测量结果，不请求模型或远程服务。

可以分别执行 `node scripts/profile.mjs build all` 和 `node scripts/profile.mjs run all`。
最后一个参数也可以使用 `native` 或 `wasm`。Node/原生测量可通过
`GOMOKU_BENCH_REPEATS`、`GOMOKU_BENCH_WARMUPS` 配置样本数，默认分别为 5、2；
浏览器使用相同的默认值。不要并发运行基准、编译或训练任务。

## 测量边界与校验

- 基准使用单搜索线程、Release 优化级别。当前默认使用 SSE2（原生 x64）或 SIMD128（WASM），没有开启 LTO；普通/诊断构建只有计时开关不同。
- `GOMOKU_BUILD_BENCHMARKS` 与 `GOMOKU_PROFILE` 默认关闭；普通网页和比赛构建不带计时插桩。
- 两个独立构建交替执行同一局面，先预热再记录。每个环境覆盖 7 个局面，每局面每构建记录 5 次。
- 固定深度搜索设 600 秒保护上限，避免计时开销触发提前中断。任何未完成的固定深度样本都会报错。
- 普通/诊断构建的最佳着、评分、主变化、完成深度和节点数必须完全一致；汇总时还核对原生/WASM 一致性。
- `wallMs` 包含重建棋盘、创建评估器、搜索和析构，不含模型下载、模型解码、JSON 编解码、JS/WASM 桥接、Worker 消息及界面渲染。
- 全量初始化在每次搜索开始执行；搜索先判断终局和置换表，只有需要继续计算的节点执行 NNUE 增量更新，分别记录。
- 31 类计时事件同时提供含子阶段和扣除子阶段的耗时。只有扣除子阶段后的耗时可以相加；脚本校验其总和等于顶层计时。
- 分阶段数据是诊断构建 5 次测量的算术平均，实际搜索速度使用普通构建的中位数，并保留最小/最大值。
- 插桩干扰用两组中位数的比值表示。没有将分项耗时按普通构建比例缩放，也没有假定计时成本均匀分摊。
- 浏览器没有开启跨源隔离，细小阶段受时钟精度影响；微秒/调用是累计时间除以调用数，不代表单次计时具有同等精度。
- 启动耗时单独记录一次。原生包含本地读文件和权重解码；WASM 分为模块初始化、复制进堆和权重解码，与网络下载时间无关。

## 2026-09-21 首次结果

基线提交 `2c0b43489593c4a0ed5d0be305c274646940b418`，在其上仅加入诊断计时和测量工具。
模型 `rapfi-calibrated-v1`；Intel Core Ultra X7 358H，Windows 11（10.0.26200），
原生 GCC 13.2.0，Emscripten 4.0.23，Node 26.3.0，浏览器 Chromium 153。
这里只报告这台机器、这组局面上的性能，不表示其他设备速度或引擎棋力。

浏览器普通构建的搜索中位数：

- 天元开局，4 层、4,941 节点：1,167.9 ms。
- 10 子开局，3 层、682 节点：151.5 ms。
- 20 子中盘，3 层、831 节点：179.4 ms。
- 39 子中盘，3 层、596 节点：129.4 ms。
- 98 子局面，3 层、725 节点：143.4 ms。
- 必防冲四，4 层、688 节点：160.9 ms。
- 一步成五，1 层、16 节点：4.2 ms；搜索确认胜势后停止迭代加深。

天元开局浏览器诊断构建的总时间平均 1,277.34 ms。其中：

- 增量空间卷积、量化与池化更新：734.16 ms，57.48%。
- Value 头及分数转换：266.98 ms，20.90%；隐藏层矩阵乘法占 243.88 ms。
- Policy 头：125.54 ms，9.83%；局部投影矩阵乘法占 66.76 ms。
- 增量线编码、查表及合并：66.82 ms，5.23%。

上述卷积阶段每个节点执行一次，4,941 次累计；每次平均约 148.59 μs。
Value 头执行 3,993 次，policy 头执行 953 次，局部 policy 投影执行 38,225 次。
候选生成与完整排序合计约 0.27%，不是当前最主要的单节点开销。

浏览器非立即胜利局面的插桩中位数差异为 +9.85%～+19.25%，原生为 +1.47%～+4.59%。
这些差异包含计时、代码布局、运行时及测量噪声；不能将诊断数据视作无扰动精确时间。
极短的原生“一步成五”样本差异为负，体现噪声，不是插桩带来了加速。

另一次开启迭代观测的浏览器搜索分别在 4.5、26.4、142.5、1,136.7 ms 完成 1、2、3、4 层。
5 次限时 300 ms 的搜索全部完成 3 层，累计访问 1,305～1,318 节点，包含未完成的第 4 层。
这解释了“300 ms、深度 3”的含义：完整第 3 层约 142 ms，其余预算继续搜索第 4 层。

原生天元开局中位数 1,019.87 ms，Node/WASM 1,131.11 ms，浏览器/WASM 1,167.90 ms。
卷积阶段在原生也占主要开销（非立即胜利局面约 67%～79%）。
当前首要的单节点优化方向是空间卷积增量更新及数值内核，其后是 value/policy 计算。
置换表等搜索优化减少访问节点数，其收益不能直接从本次阶段占比推断。

## 2026-09-21 优化后结果

本轮保持同一份权重、网络结构、数值量化和候选选择规则，没有添加 VCF/VCT 等五子棋专用战术搜索。
以下仍为相同硬件、7 个固定局面、每项 2 次预热 / 5 次正式测量；耗时是**无插桩构建**的中位数。
初始基线保存在 `docs/benchmarks/2026-09-21-before.json`；重新生成 HTML 报告即可查看前后对照。
脚本核对模型 SHA、局面、完成深度、最佳着和评分；保留节点数与主变化以便审计。
这些是开发机实测，不是 CI 性能门槛，也不能据此估计棋力提升。

浏览器 Web Worker / WASM：

- 天元开局，4 层：1,167.9 → **115.9 ms**，约 **10.08 倍**；4,941 → 3,394 节点。
- 10 子开局，3 层：151.5 → **27.0 ms**，约 **5.61 倍**。
- 20 子中盘，3 层：179.4 → **25.2 ms**，约 **7.12 倍**。
- 39 子中盘，3 层：129.4 → **22.5 ms**，约 **5.75 倍**。
- 98 子局面，3 层：143.4 → **18.9 ms**，约 **7.59 倍**。
- 必防冲四，4 层：160.9 → **23.2 ms**，约 **6.94 倍**。
- 一步成五，1 层：4.2 → **1.3 ms**；极短样本受初始化和计时粒度影响较大。

相同天元局面，原生 4 层由 1,019.87 → **96.06 ms**；Node/WASM 由 1,131.11 → **119.07 ms**。
浏览器另一次逐层观测分别在 1.5、5.1、18.8、113.7 ms 完成 1、2、3、4 层。
5 次 300 ms 限时搜索现在全部完成 **4 层**，继续搜索第 5 层，累计访问 8,837～9,021 节点；
旧版全部完成 3 层。这里是原有 16 着候选规则下的选择性搜索深度，不代表全宽穷举。

优化分两步验证：

1. **只改 NNUE 内核**时，冻结原版与新 WASM 交错运行，相同节点数、走法、评分和完整 PV 必须逐项一致。
   Node/WASM 天元 4 层为 1,120.18 → 190.01 ms，仍是 4,941 节点；7 个局面约 3.59～5.90 倍。
   中间阶段原始数据在本机 `artifacts/profiling/nnue-only/wasm.json`。
2. **再加 TT/PVS**后，天元节点为 3,394，其中 328 次直接复用 TT 结果；实际 NNUE 更新 3,066 次，
   41 次缓存着法提前剪枝省去整批 policy。PVS 并不保证每个局面的节点数都减少：10 子开局是 682 → 774，
   其中有零窗口重搜和便宜的 TT 命中，实际 NNUE 更新只有 660 次。应以耗时与有效工作量判断收益。

诊断构建中，天元空间卷积平均每次由约 148.59 → **10.98 μs**，Value 隐藏层由 61.08 → **7.68 μs**，
Policy 局部投影由 1.75 → **0.41 μs**。这些均值来自有插桩的累计时间，节点分布也发生变化，不能视作纯算子微基准。
优化后诊断扰动的相对比例更大：浏览器非立即胜利局面约 +52%～+92%；上述总加速倍数均以**无插桩**结果计算。

## 实现与正确性边界

- 缓存 11 格线特征的编码，落子时只调整受影响的三进制位；撤销时执行逆更新。
- 缓存深度可分离空间卷积的激活前累加值，传播特征差量。保留原始整数加法、ties-to-even 舍入和截断，
  不把更新后的激活值近似代回卷积；保存与恢复累加器、特征和池化状态。
- Value/Policy 点积、特征合并、卷积差量和池化更新使用精确 SIMD。点积按块扩展到 int64，防止大网络 int32 溢出；
  非 8 倍数通道有标量尾部。每个评估器复用输入与隐藏层缓冲区。
- 搜索会话各自持有 4 MiB 置换表，完整哈希包含棋盘大小、规则和行棋方，记录深度、上下界/精确分数和着法，
  并转换杀棋距离。表不跨模型或搜索会话复用，未完成节点不发布缓存结果。
- PVS 对后续着法先用零窗口，必要时完整重搜；PV 路径的内部节点保留完整搜索以重建主变化。
- TT/PV 缓存着法优先尝试，再按需计算候选 policy；部分排序保持原有 16 着选择规则，所有立即成五/防守着点仍保留。
- 终局和 TT 剪枝先于 NNUE push；RAII 确保搜索限时、节点限制、取消和异常均恢复棋盘与评估器栈。

`GOMOKU_SIMD=OFF` 可编译同数值的标量实现。WASM 默认产物使用 `-msimd128`；前端接口与模型格式不变。
`SearchOptions` 可分别关闭 TT/PVS，供固定深度基准与参考测试使用，不暴露为网页操作项。

本轮验证包括：

- 原生 SSE2、WASM SIMD128、原生标量三套核心/算子/搜索测试；CI 同时覆盖这些路径。
- 真实模型 64 个局面、192 个 Value logits、14,400 个 Policy logits，原生与 WASM 对独立 Python int64 参考的误差均为 **0**；
  原生额外通过 1,490 次增量与撤销检查。
- 15/20 路、freestyle/standard、非向量对齐宽度（7/9/5）的训练导出与运行时对齐测试。
- TT/PVS 与关闭二者的完整窗口搜索对照，包含强制槽位冲突、PV 叶点评分一致、模型切换隔离与中断恢复。
  另用真实模型的 64 个局面加 7 个基准局面核对固定深度搜索，71 项最佳着和评分全部一致。
- 三种网页对局模式、Worker/API/Gomocup 协议、NNUE 完整自对弈、训练恢复与量化导出回归测试。
